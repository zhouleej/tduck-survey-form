## 4. 首要建设方向：让每次邀请可追溯

建议先做“创建本地邀请批次 → 保存名单与内容快照 → 执行发送 → 查询并匹配明细 → 展示发送与送达结果”的完整闭环，再扩展模板创建和统计面板。

### 建议的数据模型

以下均为建议新表，并非现存结构：

1. **邀请活动**：关联 formKey、创建人、业务目的、模板绑定和公开链接策略。
2. **本地发送批次**：本地唯一 batch_id、幂等键、参数/正文快照、配置版本、发送策略、总人数、创建时间。与 provider_task_id 分开；一次本地批次也可能拆成多个网关请求。
3. **收件人明细**：关联 batch_id，保存标准化号码、按收件人的变量/链接、受理状态、发送状态、送达状态、失败原因和各阶段时间。
4. **发送尝试**：每一次网络请求的 attempt_id、所覆盖的本地明细、请求摘要、提交前时间、响应时间、响应码、可选 provider_task_id/msgid，以及失败还是“状态未知”。请求落库后再发送，以应对进程中断。
5. **回执事件/查询明细**：尽可能保存 provider_record_id、provider_task_id、msgid、custid、号码、发送时间、状态原值、同步时间及匹配依据；对身份字段确认语义后再设置唯一约束。明细中客户数据不放普通应用日志，按角色限制访问和保留时长。

**关键关联规则**：taskid 是外部长期任务线索，不足以唯一关联本地批次；同一号码可以在同一 taskid 下多次发送。如果开放 API 不支持客户端唯一标识且 msgid 为空，需要结合稳定的外部明细 ID、时间窗、号码、模板与请求快照做候选匹配。存在多个候选时标为“待关联/关联不确定”，不能只取“最新一条”强行归属，更不能用“taskid+手机号”覆盖历史。

### 状态设计

使用相互独立的维度，避免一条状态枚举挤进所有含义：

- **提交状态**：待发送、提交中、已受理、明确拒绝、受理未知。
- **发送状态**：待处理、发送成功、发送失败、未知。
- **送达状态**：等待回执、送达成功、送达失败、超时未确认/未知。未返回字段不是“送达失败”；失败可由迟到的最终回执更新，保留事件时间和到达顺序。
- **参与状态**：未访问、已访问、已提交；仅在确有归因能力后提供。短信已送达不意味着已读，也不等于填写成功。

状态映射需要保留供应商原始数值和说明；优先使用经确认的结构化字段。只有状态文本时，使用明确允许列表并标出映射来源；遇到新文本保留为未知，避免字符串包含“成功”造成误判。

### 同步与幂等

- 先实现“手动刷新回执”，验证查询端点、时间字段、分页和关联，再增加基于数据库 next_poll_at 的后台调度；启动恢复待同步记录，多实例通过数据库认领避免重复查询。
- 查询按 provider_task_id 和时间窗批量执行，使用分页、重叠窗口和明细去重。不能为同一长期任务内每个本地批次反复全量扫描。
- 查询失败可以退避重试；发送超时保持“受理未知”，先核实，不直接重发。明确终态失败、用户有意再次发送时创建新 attempt 并保留旧记录。
- 后端校验幂等键、活动/用户配额和发送频率，形成批次预览与确认；现有 UI loading 只作为交互反馈。

## 5. 模板、链接与使用体验

目前发布页默认 `p1=formKey`，只适合“域名及 /s/ 固定在模板里”的一种情况。实查模板 373518 用 5 个连续变量承载完整链接，而用户必须手工拆分，系统没有模板内容来验证变量缺失。这是优先级很高的操作风险。[代码：前端 `SmsInvite.vue:44–70,125–126,189–193`；PDF 第 14 页；本轮模板详情 n43。]

建议增加本地“云信短信模板”绑定记录：外部模板 ID、名称、固定正文或受控内容快照、普通/变量类型、变量名/顺序/必填/来源、已知审核状态和更新时间。发送页改为选择模板，按绑定自动填写问卷编号/完整链接/分段链接/联系人等字段，并提供渲染后的完整短信预览、人数、无效/重复号码及预估请求分组。模板正文获取与模板列表开放能力未在本 PDF 中给出，不能默认使用浏览器私有接口；第一阶段允许管理员录入并与供应商平台核对。

链接规则：固定域名模板优先只替换短标识；兼容历史模板时按明确配置的连续占位符数量自动拆分，必须校验每段长度、总容量、拼接一致性和非空规则，不随意把语义无关变量当成链接切片。当前模板按文档每变量最多 20 字符计算，5 段理论容量为 100 字符；较短链接如何处理剩余变量的空值/省略，应确认供应商规则，不擅自补空格。短信中的链接应使用已部署、手机可访问的问卷公开地址，不能把 `localhost:8888` 当成可对外邀请地址。短链接服务是独立后续能力，不假定云信已提供。

现有“保存至模板中心”是问卷结构复用，分类与封面来自原问卷模板功能，和云信短信模板不同。建议文案分别使用“问卷模板中心/问卷分类”“云信短信模板/普通文本、变量文本”，减少配置误解。[前端 `src/views/project/template/create.vue:3–16,47–49`；后端 `FormTemplateEntity.java:24–50`。]

## 6. 与答卷追踪的闭环

当前所有邀请接收者使用同一问卷链接、同一组变量，填写请求带 formKey/设备信息/答卷，但没有明确的邀请收件人 ID。因此现有数据只能统计问卷总访问/总提交，不能可靠计算某个短信收件人的转化率。[`FormSmsInviteService.java:43–44`；`YunxinSmsServiceImpl.java:105–109`；前端 `src/views/form/write/index.vue:223–238`；后端 `UserFormDataEntity.java:24–112`。]

可在后续引入不可猜测的邀请标识，服务端解析为收件人关联，再记录点击和提交。现有 extValue 及链接扩展结构可以作为兼容入口，但裸 query 参数不能证明身份，不能据此开放他人的数据权限。链接可能被转发，归因应称为“通过该邀请链接提交”，不声称一定由手机号本人填写；手机号不得直接放进公开 URL。个人化链接也要求发送器支持逐号变量，而不是当前所有号码复制一份变量 map。

## 7. 复用现有模块与需要补充的模块

| 现有模块 | 可复用部分 | 不应直接套用的部分 |
| --- | --- | --- |
| SmsService / SmsConfiguration | 既有渠道与验证码兼容、配置刷新、Hutool 请求 | 不宜无限扩充统一 sendSms boolean；云信客户端返回类型化结果，业务编排留在邀请服务 |
| MyBatis-Plus / BaseEntity | 批次、明细、尝试与同步游标的数据库持久化 | 不把本地内存缓存当成可靠队列或跨实例幂等存储 |
| FormAuthUtils / AuthorizationInterceptor | 表单所有者/管理员校验、系统配置管理员保护 | 新增历史/回执/导出接口必须继续按 formKey 或活动所有权检查，不能只凭 taskid 读取 |
| Spring 事件与 @EnableAsync | 将提交准备和执行异步解耦、沿用项目风格 | 目前没有调度器和持久化短信任务；单纯 @Async 不保证重启恢复 |
| WebhookEventEntity / RetryTemplate | 参考事件状态、错误、次数落库及退避模式 | 现有是向外部地址推送的出站 webhook，不是云信回执入口；其自动重试策略不能直接用于扣费短信发送 |
| Vue 2 / Element UI | 配置表单、校验、任务列表、明细抽屉、状态筛选、刷新与导出 | 只保留一次提交的 lastResult 不足以支撑任务台 |

依据：`AuthorizationInterceptor.java:41–85`；`FormAuthUtils.java:24–36`；`TduckApiApplication.java:13`；`tduck-webhook/.../AddWebhookEventListener.java:44–45`；`WebhookSenderService.java:38–75`；`WebhookEventEntity.java:40–60`；`tduck-common/.../CacheUtils.java:23–63`。

配置日志需优先修正：`tduck-api/.../listener/EnvConfigRefreshListener.java:38` 将整个环境配置序列化到 debug 日志，可能含云信鉴权材料。建议只记录配置 key、修改人和必要版本，不打印完整值。网关配置由管理员维护，保留内网网关场景，按受控地址策略约束；普通问卷用户不应自行指定任意请求目的地。

## 8. 建议分期与验收口径

| 优先级 | 交付目标 | 验收重点 |
| --- | --- | --- |
| P0 | 先绑定现用模板的内容、5 变量映射和链接预览；修正配置日志；联调开放查询的 taskid/明细标识、时间过滤、状态码及分页 | 缺失变量在发送前被阻止；链接拼接与预览一致且可由手机访问；同一长期任务下两次发送不串单；日志无凭据；未知状态不误报成功 |
| P1 | 本地批次与逐号明细持久化、幂等、人工刷新与后台回执同步、历史列表与错误原因 | 刷新和重启不丢任务；超时不重复扣费发送；多页查询无遗漏且事件可去重；发送与送达分开展示 |
| P2 | 扩展模板选择与管理、批量导入预校验、逐号个性化、失败名单导出 | 多模板映射正确；正文与模板一致；预览人数与实际发送人数可核对；人工重发只覆盖明确选择的人 |
| P3 | 邀请链接归因、点击/提交漏斗、上行回复、可验证的退订/联系偏好处理 | 点击、送达、提交统计口径明确；转发不被误认身份；上行同步 24 小时分窗可恢复且去重 |
| 后置 | 模板在线创建/审核、跨运营商覆盖展示、云信长期任务暂停/恢复/换模板、可能的回调 | 先确认开放 API/权限与影响范围，不用网页内部接口当作稳定集成协议 |

待供应商或后续联调确认：开放 API 是否支持返回稳定的逐条 ID、客户端关联 ID或查询发送序号；查询字段和分页上限；msgid/custid 的准确语义；送达状态字典及长期未回执规则；是否支持主动回调及其签名/重放/重试协议；配额、并发和限流；长短信计费/分段统计口径；网页模板列表、余额、导出等能力是否有正式开放接口。

### 建议下一轮的最小可交付范围

按“模板绑定与预览 → 持久化发送历史 → 人工查回执 → 自动同步”的顺序推进；自动同步依赖正式开放查询联调成功，不为赶进度绑定浏览器登录态。

- 后端将云信协议封装为发送、查询、审核各自的类型化方法；网站内部字段与正式开放 API 字段独立映射，保留原始状态和来源。当前只接已有正式协议可支持的部分。
- 问卷“短信邀请”页增加“发送邀请 / 发送记录”两个入口：邀请界面显示模板名称、内容预览、完整链接和有效人数；记录界面显示本地批次号、受理/发送/送达人数、更新时间，明细显示失败原因和“状态未知”。
- 首个版本无需复制云信的全部报表和模板编辑器，也无需引入新的队列基础设施；复用现有数据库、服务权限与 Element UI，先让一批邀请在刷新和服务重启后仍能追踪。
- 验收使用模拟网关覆盖超时未知、同号重复批次、空 msgid、迟到/重复回执和多页重叠；正式平台仅在授权后做最少量联调。当前只读调研不额外发送短信来补证。
